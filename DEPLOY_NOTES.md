## ZOMBO 0.23 · экономика

Обновление добавляет read-only отчёт `/api/admin/economy/flows`, вкладку в Mini App и изолированную CLI-симуляцию. Существующие ставки, награды, платёжный баланс, БД игроков и SQL-модели не меняются; новой миграции нет. Сохранить прежний pre-deploy `python scripts/migrate.py`, проверить GitHub CI и Railway `/ready`. Симуляцию можно запускать только для анализа, она ничего не записывает в production. Права отчёта — только `ADMIN_IDS`.

# Передача для GitHub и Railway

База изменений — `main` коммит `c0b0ce4bdb45cd00debd7a88a5db01a453abb7de` (0.16); версия кода в архиве — 0.21.0. Перед загрузкой ещё раз сравните с текущим `main` и перенесите изменения через проверяемый PR. Архив содержит полные исходники; он не должен подменять секреты или базу данных. Этот пакет не загружался в production.

1. На отдельной PostgreSQL запустите `scripts/verify_migration_pg.py`, `scripts/verify_clan_pg.py` и `scripts/verify_concurrency_pg.py`. Для первого и третьего нужны `DATABASE_URL=postgresql+psycopg://.../<имя>_test` или `_ci`, `ZOMBO_TEST_DATABASE=1`, `DEMO_MODE=1`, пустой `BOT_TOKEN` и `PUBLIC_URL`. CI задаёт эти значения и запускает сценарии последовательно. При ошибке CI пакет не выпускать до исправления причины.
2. Запустите `python -m pytest -q tests`, `python -m compileall -q app.py game.py gear.py clan_missions.py security.py notifications.py world_events.py encounters.py scripts tests` и `node --check static/app.js` на Python 3.11 с `requirements.txt`.
3. После резервного копирования выполните `python scripts/migrate.py --check` на тестовой копии PostgreSQL, затем `python scripts/migrate.py` там же. Повторите эти два шага на целевой БД **до запуска версии 0.21**: production больше не создаёт недостающие таблицы при старте. Мигратор добавит `schema_migrations` и семь таблиц: `notification_category_optins`, `clan_season_contributions`, `clan_season_settlements`, `clan_season_results`, `clan_season_reward_claims`, `encounter_clues`, `resource_ledger`. Если проверка обнаружит дрейф схемы, остановитесь и разберите его вручную; не удаляйте данные ради продолжения. Элитный модификатор хранится в журнале боя, прежние бои продолжаются как обычные.
4. Оставьте действующие `ADMIN_IDS`, платёжные настройки, расписание offsite backup и секреты в Railway. Проверьте после выкладки новую таблицу зацепок, вкладку журнала ресурсов и ветки встреч в городе и встречный бартер, одну продажу снаряжения, элитный бой, награды рейда/экспедиции, `/ready`, Telegram-бота и вкладку диагностики админки. Для уведомлений включите тестовую учётную запись, запустите рейд и назначьте бойца на КВ; проверьте очередь и доставку. Итоги сезонов фиксируются после 01:00 UTC первого числа; личная награда доступна только за следующий завершённый месяц с сохранённым вкладом. Реальные Stars тестировать только по отдельному плану.

Журнал ресурсов начинает хранить движения после обновления; старые операции не переносятся. На тестовой PostgreSQL проверьте запись и откат одной покупки, боя и Stars, оцените рост таблицы и размер бэкапа. Не очищайте журнал без отдельной политики хранения.

Откат к предыдущему коду не требует удаления новых таблиц: старая версия их игнорирует. При сбое сначала остановите новые операции, затем верните предыдущий проверенный релиз; не откатывайте саму PostgreSQL без отдельного решения о данных, появившихся после обновления.
